## 1. v1.1 交代的驗證項目

### 1.1 懸吊三模態穩定性重新驗算（v1.1 §4.3 指示事項 6）

新幾何的輪距由 0.09 縮至 0.056、`I_zz` 由 1.024e-4 降至 5.779e-5，
三個模態的 K 值全部重算：

| 模態 | K | r = 1 − c·K（c = 2.0） | 穩定上限 |
|---|---|---|---|
| heave | 0.2222 | 0.5556 | c < 9.00 |
| pitch | 0.1740 | 0.6520 | c < 11.49 |
| roll | 0.4522 | **0.0955** | c < 4.42 |

三者皆滿足 `|r| < 1`，**c = 2.0 在新幾何下仍然有效，無須重新求解**。
roll 模態幾乎達到 deadbeat（r ≈ 0.10），比 v1.0 幾何下的 −0.318 更好 ——
輪距變窄使 `I_zz` 與力臂平方同步下降，兩者相除後 K 反而略減。

彈簧側：`ω_n·dt` heave = 0.745、roll = 1.063（顯式積分上限 2.0），
roll 由 v1.0 的 1.284 降到 1.063，離穩定邊界更遠。

實測（平地直線行駛 0.5 秒，全程無碰撞）：

```
max|ω_roll| = 0.000 rad/s   max|ω_pitch| = 0.454 rad/s   最大傾角 0.76°
行駛高度 28.86 ~ 29.42 mm
0.5 秒後車速 1.461 m/s，理論上限 μ·g·t = 1.472 m/s
```

此測試同時作為自動化驗收，見 `tests/acceptance.test.ts`
「顯式阻尼在 heave / pitch / roll 三個模態都滿足 |1 − c·K| < 1」。

### 1.2 質量屬性完全由幾何衍生（v1.1 §3.2）

`hullInertia()` 探測世界機制已移除。兩個 collider 各自 `setMass()`，其餘交給 Rapier：

### 1.3 實測靜態行駛高度與 §7 的 `y` 下界（v1.1 §4.2、§5）

自 y = 0.06 落下，600 幀後收斂：

```
車體原點 y      0.02904 m       （預測 0.02877）
車體最低點離地   0.01904 m
```

`實測靜態高度 + 0.001 = 0.0300`，**與 v1.1 給定的 `y` 下界 0.030 完全吻合，維持不變**。

這個吻合不是巧合：錨點在 `y = −0.005`、restLength = 0.025，
所以「懸吊恰好處於自由長度」的車體原點高度正是 `0.005 + 0.025 = 0.030`。
換句話說 `y = 0.030` 是懸吊零壓縮的臨界點，衝突 C 描述的異常地帶被完全排除。

另一項設計上的巧合值得記錄：錨點與車體最低點的落差
`−0.005 − (−0.010) = 0.005 = restLength − maxTravel`，
因此懸吊恰好用完 `maxTravel = 0.020` 的行程時底盤才觸地。

### 1.4 圍欄無縫隙（v1.1 §1.2 標示的最主要風險）

自 stadium 中心線朝 1440 個方向、4 個高度（0.005 / 0.02 / 0.04 / 0.055 m）射線：

```
落空次數                 0 / 5760
|命中距離 − R| 最大值     0.00302 m
```

3.0 mm 的誤差全部是**外凸**（平面段以弦逼近圓弧，段中央相切、段邊緣外移），
不會形成內凹的卡車口袋。重疊係數 1.15 產生的實際重疊量：
在內緣半徑 0.35 處每段半弦長 0.0606 m 對上半段弧長 0.0458 m，重疊 32%。

此測試同樣納入自動化驗收。

### 1.5 §6.3 幾何斷言

v1.1 §4.1 的兩項條件都以 assertion 驗證且**嚴格成立**：

1. 所有錨點在底盤水平投影內：`|x| = 0.028 < 0.035`、`|z| = 0.035 < 0.050` ✓
2. 錨點高度 `y = −0.005` 嚴格高於車體最低點 `y = −0.010` ✓

另外保留 v1.0 的刮地檢查：靜態行駛時車體最低點（−0.010）嚴格高於接觸面（−0.0290）✓

**一處措辭需要確認**：v1.1 §4.1 說「錨點上移 0.005 後，完全壓縮時的接觸高度 y = −0.005
嚴格高於 hull 最低點 y = −0.010，v1.0 §6.3 的原斷言自然成立」。但 v1.0 §6.3 的原文是
「**車體 hull 的最低點必須高於**懸吊完全壓縮時的接觸高度」，方向相反 ——
按原文，−0.010 並不高於 −0.005。實作採用 v1.1 §4.1 明確寫出的條件（錨點高於最低點），
這也是唯一在新幾何下可檢驗且成立的版本。兩者的物理意義其實相同：
底盤在懸吊用完 `maxTravel` 時才觸地，正常行駛不可能達到。

## 2. 與 v1.1「預期變化」不符的觀測

v1.1 §8 要求：「若實測與上述方向明顯相反，代表某處實作有誤，應先釐清再繼續。」
以下兩項與預期不符，已釐清成因，但請確認是否接受。

### 2.1 逾時率：預期下降，實測**上升**（80 → 97 / 500）

v1.1 預期「場地面積由 0.81 m² 降至約 0.60 m²，逾時率下降」。實測相反。

成因不是實作錯誤，而是**形狀**而非面積主導了結果：

- v1.0 的正方形有四個角落。車輛撞進角落會被兩面牆同時作用而爬升、翻出，角落是主要的出場機制。
- v1.1 的 stadium 是處處光滑的凸邊界。車輛沿弧形圍欄內側進入**穩定的漂移環繞**：
  殘留的偏航角速度使車頭持續轉向，驅動力與 μN 的側向摩擦力達成平衡，形成極限環。

逐幀追蹤一場逾時戰鬥（`sample_battles/draw_timeout.json`）可以看得很清楚：

```
frame    A: stadium 距離   y        |v|      up      B: 距離    y        |v|      up
  1600      0.3112      0.0314    3.367    1.000       0.3121   0.0312   3.232    1.000
  3200      0.3118      0.0312    2.722    1.000       0.3116   0.0311   3.020    1.000
  6400      0.3062      0.0311    3.273    1.000       0.3116   0.0311   3.052    1.000
  7200      0.3138      0.0310    3.260    1.000       0.3144   0.0311   3.341    1.000
（圍欄內緣在距離 0.35）
```

兩車正立、貼地、以約 3.3 m/s 在固定半徑上繞行，60 秒都不脫離也不相遇。

戰鬥長度呈明顯的雙峰分布：

```
0–600 幀: 299 場   |  600–7200 幀: 104 場   |  7200 幀（逾時）: 97 場
```

60% 的戰鬥在 5 秒內結束，19% 進入永久環繞。這是規格所定義的物理模型的自然湧現行為
（無轉向、無偏航阻尼、光滑凸邊界），不是 bug。**但它直接造成 §11.5 無法達成，見第 3 節。**

### 2.2 角速度峰值：預期上升約 36%，實測**下降** 5.6%（89.2 → 84.2 rad/s）

v1.1 預期「新幾何底盤更窄，`I_yy` 預估降至約 1.8e-4，峰值上升至約 140 rad/s」。

實測 `I_yy = 2.7989e-4`，相對 v1.0 的 2.83e-4 只降了 **1.1%**，不是 36%。

原因是預估只考慮了底盤變窄，忽略了**前武器的平行軸項**：前武器質量 0.04 kg，
其質心距全車質心約 0.048 m，貢獻 `m·d² = 0.04 × 0.048² ≈ 9.3e-5`，
恰好補回底盤變窄損失的量。

因此角速度峰值幾乎不變（84.2 vs 89.2）。**這對驗收是好消息**：
400 rad/s 的上限提供 4.8 倍餘裕（而非預估的 2.9 倍），
500 場隨機投擲中 clamp 觸發 **0 次**，§11.2 完全達成。

其餘預期方向全部吻合：

| 預期 | 實測 |
|---|---|
| 翻覆率上升 | FLIP 64 → **106** / 500 ✓ |
| 翻覆臨界 μ 由約 1.7 降至約 0.9 | 實測 **0.897**（cogHeight 0.03123 m）✓ |

## 3. §11.5：v1.2 已裁決，改以平行化解決（已達標）

> **v1.2 更新**：本節原本回報「30 秒預算無法達成」並提出縮短時限或放寬預算兩個方向。
> v1.2 §1.1 兩者皆不採納，裁決正確 —— 我的分析全部建立在單執行緒的前提上，
> 而該前提本身就是問題所在。500 場模擬彼此完全獨立，是可完美平行化的工作負載。
>
> 改以 worker pool 平行執行後：
>
> | 指標 | 結果 |
> |---|---|
> | §11.5a 批次吞吐（12 workers） | **7,694 ms**（上限 30,000 ms）✅ |
> | §11.5b 單場成本（單執行緒） | **20.44 µs/car-frame**（上限 50 µs）✅ |
>
> 平行化取得 **5.8 倍**加速；相較之下單執行緒微優化只拿到 4%。
> `--workers 1` 與 `--workers 12` 的 CSV 位元完全相同。
>
> 以下 3.1 / 3.2 的量測保留，因為它們仍是 §11.5b 的依據，也解釋了為何單執行緒優化到頂了。

### 3.1 這不是「每幀太慢」，而是「總幀數太多」

```
總幀數          1,067,140
其中逾時場次     698,400  (65%)   ← 97 場 × 7200 幀
其餘 403 場       368,740  (35%)
每幀成本         42.1 µs（逾時場次與其餘場次幾乎相同，無異常場次）
```

若逾時場次不存在，368,740 幀只需 **15.5 秒**，§11.5 輕鬆達標。
問題完全來自 2.1 描述的穩定環繞。

### 3.2 每幀成本已逼近 Rapier 的下限

逐段量測一場 7200 幀的真實戰鬥：

| 區段 | µs/frame | 佔比 | 可否降低 |
|---|---|---|---|
| 8 次懸吊 raycast | 12.5 | 27% | ❌ 幾乎全是 JS↔wasm 邊界成本 |
| `world.step()` | 22.4 | 48% | ❌ Rapier 內部（CCD、8 次 solver 迭代皆為規格強制） |
| 本專案的 JS 運算 | 6.7 | 15% | ⚠️ 部分可降 |
| clamp / 判定 / checksum | 3.3 | 7% | ⚠️ 已優化 |

raycast 的成本與場景大小幾乎無關（1 個 collider 時 1.006 µs、27 個 collider 時 1.102 µs），
**約 1 µs 是純粹的繫結開銷**，不會因為簡化場地而改善。

已實施的最佳化（純實作層面，數值位元完全相同）：
**每幀只跨 wasm 邊界讀一次剛體狀態**（原本懸吊、clamp、判定、checksum 各讀一輪，
共 12 次以上），500 場耗時由 46.8 秒降到 44.9 秒。

也驗證過幾條無效的路：

- 把 26 段圍欄合併到單一 Fixed 剛體：**0～1% 差異**（成本在 collider 數量而非剛體數量）
- Node 的 `--max-semi-space-size=64` 降低 GC 壓力：**0.3% 差異**（瓶頸不在 JS 配置）

即使把本專案的 JS 成本全部歸零，Rapier 本身仍需
`1,067,140 × (12.5 + 22.4) µs = 37.2 秒`，**仍然超過 30 秒**。

### 3.3 §8.3 時限維持 7200 幀，且實測數據支持這個決定

v1.2 §2.2 指出我當時提供的分桶（`0–600 / 600–7200 / 7200`）不足以評估縮短時限的代價。
這個批評成立。§3 要求的直方圖已補上，數據如下：

```
  3600-4800   22 場   OUT 7, FLIP 15
  4800-6000   15 場   OUT 6, FLIP 9
  6000-7200   12 場   OUT 4, FLIP 8
```

**共 49 場（9.8%）落在 3600–7200 幀。** 若當初把時限砍半，這 49 場真實分出勝負的戰鬥
會被誤判為平手。維持 7200 是正確的。

## 4. §16 跨平台決定性：本機驗證通過，多架構矩陣待 CI

依 v1.2 §8 的執行順序，§16 優先於平行化實作，已先完成。

### 4.1 本機可執行的驗證全部通過

20 組 fixture（44,802 幀，含四場 7200 幀的混沌環繞），在同一台機器上以
**不同的 V8 代碼產生路徑**交叉比對 —— 這是本機能取得的、最接近「不同平台 codegen」的對照：

| 執行方式 | 結果 |
|---|---|
| 預設 | 20/20 一致 |
| `--liftoff-only`（wasm 只用基準編譯器） | 20/20 一致 |
| `--no-liftoff`（wasm 只用 TurboFan） | 20/20 一致 |
| `--no-wasm-tier-up` | 20/20 一致 |
| `--no-opt`（JS 最佳化編譯器停用） | 20/20 一致 |
| `--single-threaded` | 20/20 一致 |

Liftoff 與 TurboFan 是兩套完全不同的機器碼產生器（不同的暫存器配置、指令選擇），
兩者對同一份 wasm 產生位元相同的浮點結果，代表分歧不會來自 codegen 層。

### 4.2 §7.4 的 SIMD 疑慮：這份 build 沒有 SIMD

直接解析 `rapier_wasm3d_bg.wasm` 的 section：

```
type section 內的 v128 (0x7B) 出現次數     0
code section 內的 0xFD 前綴比例            0.009%（隨機位元組基準約 0.4%）
wasm 檔 SHA-256   1ce1c8c4036b4dcd3bde86c6efdb0f270cf5e274979b1de6ab8052947ef166c5
```

**`@dimforge/rapier3d-compat@0.19.3` 是非 SIMD build，不存在 SIMD／純量路徑分歧的問題。**
（runtime 本身支援 SIMD：`wasmSimdSupported: true`；但這份 wasm 沒有用到。）

Node 24 已移除 `--no-experimental-wasm-simd`（SIMD 已 ship），因此無法用旗標對照；
改以靜態分析取得更確定的答案。CI 有一道檢查會在 Rapier 換成 SIMD build 時直接失敗。

順帶一提：廣為流傳的 wasm-feature-detect SIMD 偵測位元組在 Node 24 上驗證失敗
（模組本身格式有誤，code section 長度少一），本專案改用自行組出、已確認可 instantiate 的版本。

### 4.3 支持跨平台一致的結構性事實

- **Rapier 的 wasm 不 import 任何 JS 數學函式** —— 32 個 import 全部是 wasm-bindgen 的
  物件橋接與 typed array 建構子，浮點運算全部編譯在 wasm 內。
  WebAssembly 規範要求 f32/f64 運算位元精確（IEEE-754、round-to-nearest-even、
  無延伸精度、無 FMA 合併），這是本專案跨平台一致性的主要依據。
- **本專案 JS 端的每幀熱路徑只用到 `+ - * /` 與 `Math.sqrt`**，全部是 IEEE-754 正確捨入的運算。
  `Math.sin` / `cos` / `tan` 只出現在圍欄佈局與初始朝向，屬建構期。

### 4.4 `Math.hypot` 風險點 —— v1.3 已核准變更並修正

> **v1.3 更新**：本節原本評估「只與門檻比較……最壞影響是結束幀差一幀」。
> 設計方在 v1.3 §1.2 上修了這個評估，而且是對的：
>
> 出界判定決定**終止幀**，終止幀決定 **checksum 陣列的長度與最後一筆內容**。
> 兩平台在不同幀終止 → 陣列長度不同 → `--compare` 直接失敗 → §11.8 不通過。
> 更嚴重的是若某車擦過門檻的那一幀另一車正好 FLIP，依 §8.4 `result` 會由
> `A_WINS` 變成 `DRAW` —— **勝負可跨平台不一致**，不是「差一幀」。

`stadiumDistance()` 已改為 `Math.sqrt(x*x + dzz*dzz)`。變更後**每幀熱路徑上不含任何
精度為實作定義的運算**（只剩 `+ - *` 與 `Math.sqrt`，全部 IEEE-754 正確捨入）。

`Math.hypot` 唯一的優勢是避免中間值平方時的溢位／下溢；本專案 |x| ≤ 0.55、|dzz| ≤ 0.45，
平方後量級 1e-1 ~ 1e-7，距 f64 溢位邊界有數百個數量級餘裕，該優勢無從發揮。

**變更後重測，行為完全中性：**

```
500 場勝負分佈    A_WINS 203 / B_WINS 200 / DRAW 97      （與變更前完全相同）
結束原因          OUT 297 / FLIP 106 / TIMEOUT 97        （相同）
總幀數            1,067,140                              （相同）
20 組 fixture     全部 checksum 一致                      （相同）
5 個 sample_battles 結局與幀數                            （相同）
```

也就是說兩種寫法在這個數量級下本來就給出相同結果，變更移除的是**可攜性風險**而非改變行為。

環境指紋依 v1.3 §1.4.3 **保留** `hypotMatchesSqrt` 欄位（本機實測 `false`），
作為未來若有人重新引入 `Math.hypot` 的迴歸偵測。
另於 `eslint.config.js` 新增 §3 禁令 7 規則（`no-restricted-properties`），
在 `src/sim/` 直接擋下 `Math.hypot` 等 19 個精度為實作定義的函式；
`world.ts` 與 `types.ts` 為建構期例外，已在設定檔中逐一說明理由。

### 4.6 CI 部署上的一個坑

專案位於 `darkbearlab/misc` 的 `crush_gear/` 子目錄，而
**GitHub Actions 只讀取 repo 根目錄的 `.github/workflows/`** ——
子目錄裡的 workflow 完全不會被載入，推上去也不會有任何 job，很容易誤以為「CI 綠燈」。

解法是在 repo 根目錄放一份適配版（`.github/workflows/crush-gear-platform-determinism.yml`）：
以 `defaults.run.working-directory: crush_gear` 切換 `run:` 步驟的工作目錄，
但 `uses:` 步驟不受其影響，其 `path` 仍相對於 workspace 根目錄，
因此 artifact 的路徑必須明寫 `crush_gear/` 前綴。

## 5. 已知偏離：§11.1 的「逾時平手」情境只跑 20 次

### 5.1 偏離內容

§11.1 要求「任一組輸入參數，連續執行 100 次，checksum 陣列完全一致」，
且至少涵蓋 10 組不同的投擲參數。

`tests/determinism.test.ts` 涵蓋 10 組情境，其中 **9 組跑滿 100 次**，
唯獨「逾時平手（跑滿 7200 幀）」只跑 **20 次**。

### 5.2 成本理由

該情境每次都要推進滿 7200 幀，是其他情境的數十倍：

| 次數 | 該情境耗時 | 測試套件總耗時 |
|---|---|---|
| 20（目前） | 約 6.4 秒 | 約 140 秒 |
| 100（規格要求） | 約 32 秒 | 約 165 秒 |

單次約 320 ms，補足到 100 次要多花約 26 秒，使套件增加約 18%。

### 5.3 風險評估

偏離的實質風險低，但**不為零**：

- 決定性若會失效，長場次是最容易暴露的情境（累積誤差最大），
  因此「只跑 20 次」正好落在最該加強的地方 —— 這是這項偏離唯一真正的疑慮。
- 另一方面，同一場戰鬥的 7200 幀本身就是 7200 次連續的狀態推進，
  20 次重複已提供 144,000 幀的比對量，遠多於其他情境的 100 次重複。
- §16 的跨平台 fixture 中另有 **4 組 7200 幀的環繞場次**（`orbit_01`~`orbit_04`），
  每次 `--compare` 都會逐幀（dense）比對，等於再一層長場次的覆蓋。

### 5.4 若要消除此偏離

| 選項 | 成本 | 代價 |
|---|---|---|
| 直接改成 `repeats: 100` | 套件 +26 秒（140 → 165 秒） | 無，只是慢 |
| 以 worker pool 平行跑這 100 次 | 套件 +2～3 秒 | 變成跨 worker 比對，與 §1.3 既有的測試在語意上重疊，且不再是「同一行程內重複」 |

目前維持 20 次並記錄於此，**待設計方裁決**。
