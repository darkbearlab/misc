# Phase 1.5 物理調校 — 基線與流程

設計方將調整**車體尺寸**與**輪胎摩擦係數 μ**。此變更會使 `PHYSICS_VERSION` 由 1 升至 2。

本文件是調校的對照組與操作手冊。**目前尚未變更任何數值** —— 以下全部是 v1 的實測基線。

- 物理規格見 [SPEC.md](SPEC.md) §5–§8
- Phase 0 的調參紀錄見 [TUNING.md](TUNING.md)
- 重跑基線：`npx tsx tools/baseline-report.ts`（人可讀）或 `--json`（可 diff）
- 參數掃描：`npx tsx tools/mu-sweep.ts`（見 §1.6）

### 探索用的參數覆寫

掃描不永久修改 `constants.ts`。`simulate()` 接受一個可選的 `physics` 覆寫
（`PhysicsOverride`，只開放 §6.5 明文允許調整的 μ 與 `wheelSurfaceSpeed`）：

```bash
npx tsx tools/baseline-report.ts --mu 0.20
npx tsx tools/mu-sweep.ts 0.30 0.22 0.18
```

覆寫以**純參數**傳入，`src/sim/` 不會因此讀取任何 I/O、環境變數或牆上時間。
不指定覆寫時，傳給輪胎模型的就是 `constants.ts` 的同一個 double，
因此預設路徑與寫死常數時**位元完全相同**（以 `verify-platform --compare` 20/20 證明）。

> **覆寫僅供探索。** 選定的值必須寫死回 `constants.ts` 並升 `PHYSICS_VERSION`；
> 掃描結果不得作為版本依據。

### 1.5 判讀時的兩個陷阱

**FLIP 率下降不必然是壞事。** 現有 106 場 FLIP **全部是「撞飛式翻覆」**，
沒有任何一場是實物中最主要的「鏟起式翻覆」——`WEAPON_HULL` 最低點 `y = -0.005`
高於底盤最低點 `y = -0.010`，武器在幾何上碰不到對手車底（`PHASE2_BACKLOG.md` 第 1 項）。
在鏟形武器上線前，FLIP 率只反映撞飛的頻率。

**μ 對環繞的影響方向未知。** 側向摩擦變小可能更易脫離弧線，也可能更難被推出場。
這一項只能實測，不要事先假設方向。

### 主要結論：**降低 μ 會惡化環繞，不是緩解**

逾時率單調上升 **19.4% → 33.0%**，方向與「車體放大／μ 降低可能自然減輕環繞」的預期**相反**。

機制上兩個效應同向疊加：

- 加速度上限 `μg` 下降 → 車速下降 → 撞擊動能下降 → **更難把對手推出場**
- 側向摩擦下降 → 更難改變方向 → **沿牆等速滑行更穩定**，環繞反而更容易維持

**因此 §15 驅動切換機構的優先序不應下調。** 環繞無法靠調降 μ 解決。

### 次要觀察

**場上互動導致的出場幾乎消失。** OUT 幾乎全部集中在開場 120 幀（投擲直接飛出去）：

| | 0–120 幀的 OUT | 其餘區間的 OUT | 開場佔比 |
|---|---|---|---|
| μ = 0.30 | 252 | 45 | 85% |
| μ = 0.10 | 249 | 5 | **98%** |

μ = 0.10 時中段區間幾乎只剩 FLIP，「被推出場」這個結局在實質互動中不再發生。

**角速度尖峰與 μ 無關。** p50 隨 μ 單調下降（37.0 → 28.0），但 p90 / p99 / max 幾乎不動
（53 / 72–78 / 84–90）。這與 §6.3 的運動學推導一致 —— 尖峰由碰撞衝量、幾何與 §7 的投擲速度決定，
不是摩擦力造成的。**調 μ 不會改變 clamp 的餘裕。**

**線速度峰值幾乎不變**（5.072 → 5.082），由投擲初速上限決定而非 μ。

**`μg` 加速上限在所有 μ 下都成立** —— 實測/理論穩定在 0.993–0.995。

**翻覆臨界 μ 恆為 0.897**（只取決於幾何），對照組行為正確。
現行所有 μ 值都遠低於它，因此不會有自發翻覆。

**FLIP 率下降但非單調**（21.2 → 19.4 → 16.0 → 18.6 → 16.2），且依 §1.5 的第一個陷阱，
在鏟形武器上線前這個數字不宜作為好壞判準。

### 未選定

依指示本輪不選定 μ，等待設計方指定 2–3 個候選值後以播放器判斷手感。

## 1.7 第二輪:場地尺寸掃描

`npx tsx tools/arena-sweep.ts`(μ 維持 0.30,車體常數完全不動,`PHYSICS_VERSION` 未升版)

維持 stadium 形狀等比縮放 R 與 L。出界門檻、26 段圍欄、地板 cuboid、投擲合法範圍
全部由 `resolveArena()` 連動重算,**每組都重跑 5760 條射線的圍欄無縫隙測試**。

依據見 [PHASE2_BACKLOG.md](PHASE2_BACKLOG.md) §0.2:實物車長 15–20 cm、官方場地推估 40–50 cm 級,
場地邊長約為車長的 2.5–3 倍。

**本節數據為第二次執行**,採 §7 修訂後的投擲餘裕(與車長掛鉤,`VEHICLE_MAX_RADIUS + 0.02` = 0.1201 m)。
五組**一致**採新餘裕,包含基線組 —— 因此基線這一組走的是覆寫路徑,
**不是 `PHYSICS_VERSION = 1` 的預設路徑**,其數字不可與 §1.3 的 v1 基線直接對照。
第一次執行(舊餘裕 0.08 m)的數據已被本表取代;結論的差異見「與第一次執行的差異」。

### ⚠ 方法學限制(比較時必讀)

各組的投擲合法範圍為 `R − 0.1201`,隨 R 縮小而縮小,因此**每組的輸入分布不同**。

**這不是嚴格的單變數實驗。** 場地尺寸與投擲分布兩個因子同時變動,兩者的效果在此無法分離 ——
例如 S4 的秒殺率 77.0%,無法斷定有多少來自「場地小、容易出界」、多少來自
「合法投擲區只剩半徑 0.055 m,兩車必然投得很近」。

這是縮放場地的**必然結果**,不是工具的缺陷:合法投擲區由 R 定義,
不可能一邊縮場地一邊沿用同一組投擲點(舊投擲點在小場地中不合法)。
第一輪的 μ 掃描沒有這個問題 —— 五組跑的是同一批投擲,那才是嚴格的單變數實驗。

因此:
- 本表**可用於**「哪一組整體表現較好」的比較(這正是要選的東西)。
- 本表**不可用於**「場地尺寸單獨造成多少影響」的因果歸因。
- 所有結論的強度須據此打折,尤其是 S3 / S4 —— 見下方「生成重疊」。

### 圍欄穿入問題已解決

第一次執行的核心發現 —— 投擲餘裕 0.08 m 小於車體最大半徑 0.10008 m,
導致投在邊界的車刃口生成在圍欄內部約 20 mm 深 —— 在 §7 修訂後**完全消失**:
五組的「生成刃口穿牆」皆為 **0.0%**(每組取樣 400 次)。

### 新問題:生成時兩車互相穿插

換掉舊問題之後,浮現的是**另一個**幾何問題,而且它隨場地縮小急遽惡化:

| | 基線 | S1 | S2 | S3 | S4 |
|---|---|---|---|---|---|
| 生成即穿插 | 4.5% | 9.0% | 11.5% | 15.0% | **33.0%** |
| 穿插 > 2 mm | 4.0% | 9.0% | 11.5% | 14.0% | **32.0%** |
| 最深穿插 | 39.6 mm | 40.9 mm | 30.0 mm | 43.2 mm | 33.3 mm |

(每組取樣 200 場,量測 `contactDist < 0` 的接點。)

這**不是**本輪引入的:基線就有 4.5%,兩台車各自獨立取樣就有機率落在同一位置。
但比例從 4.5% 升到 33.0%,而穿插場次一開場就被解算器以巨大排斥脈衝彈開 ——
那不是玩家投出來的結果,是數值產物。S4 有三分之一的場次如此開場。

### S3 / S4 的合法投擲區容不下兩台分離的車

保證兩車不重疊所需的中心距 = `2 × VEHICLE_MAX_RADIUS` = **0.2002 m**(最壞情況:兩車刃口相對)。
各組合法投擲區(stadium)的尺寸:

| 組別 | 投擲區 X 寬 | X 寬 / 需求 | 投擲區 Z 長 | Z 長 / 需求 | X 向可分離 |
|---|---|---|---|---|---|
| 基線 | 0.4598 | 2.30 | 0.7598 | 3.80 | ✓ |
| S1 | 0.3598 | 1.80 | 0.6168 | 3.08 | ✓ |
| S2 | 0.2598 | 1.30 | 0.4738 | 2.37 | ✓ |
| S3 | 0.1798 | **0.90** | 0.3598 | 1.80 | **✗** |
| S4 | 0.1098 | **0.55** | 0.2598 | 1.30 | **✗** |

**S3 與 S4 的合法投擲區在 X 方向比一組車距還窄** —— 兩車只能沿 Z 軸分離,
投擲區實質退化為一維。S4 更極端:Z 向也只剩需求的 1.30 倍。

依裁決的判準(「若某組的合法投擲區小到無法容納兩台車的分離投擲,直接回報該組不可用」):

- **S4 判定不可用。** 33% 的場次開場即穿插,投擲區 X 向僅 0.55 組車距,
  Z 向 1.30 組。它的統計數字(秒殺 77.0%、有觀賞長度 7.4%)有相當比例來自
  「兩車被迫投在一起」而非場地尺寸本身,不構成有效樣本。
- **S3 邊緣,但未達不可用。** X 向 0.90 組車距(略低於 1)、穿插 15.0%。
  仍能產生分離投擲,只是分布明顯偏向近距離開場。其數字須以此打折解讀。
- 基線 / S1 / S2 三組的投擲區在兩個方向都寬於一組車距,樣本有效。

### 主要結論:逾時率**非單調**,S2 仍是轉折點

```
TIMEOUT   基線 18.4%  →  S1 16.6%  →  S2 10.8%  →  S3 14.4%  →  S4 15.6%
                                        ↑ 最低
```

縮小場地到 S2 為止,逾時率下降 7.6 個百分點;再縮反而回升。
**S2(R = 0.25 / L = 0.214,0.50 × 0.71 m)是本輪五組中逾時率的最低點**,
且是仍具備有效樣本的三組中最小的一組。

第一次執行(舊餘裕)得到相同的形狀與相同的轉折點,S2 逾時 10.4%。
**換餘裕沒有改變這個結論**,這是它的主要佐證。

### 秒殺率單調上升,吃掉可看的場次

```
0–120 幀   基線 52.2%  →  S1 59.2%  →  S2 62.2%  →  S3 69.8%  →  S4 77.0%
120–7199   基線 29.4%  →  S1 24.2%  →  S2 27.0%  →  S3 15.8%  →  S4  7.4%
```

秒殺率隨場地縮小**單調上升**,沒有轉折。逾時降下來的部分,大多轉為秒殺而非可看的長度。
「有觀賞長度」的比例在有效樣本三組中以基線最高(29.4%),S2 次之(27.0%),S1 反而最低(24.2%) ——
三者相差 5.2 個百分點,以 500 場的樣本量不足以區分。

### 考據與可玩性在此不一致

[PHASE2_BACKLOG.md](PHASE2_BACKLOG.md) §0.2 推估的 2.5–3 倍車長對應 **S3**(2.8 倍)。
但 S3 的逾時率(14.4%)高於 S2,秒殺率(69.8%)明顯較高,可看場次僅 15.8%,
且其投擲區已在「容不下兩台分離的車」的邊緣。

**考據最接近的一組,不是統計上最好的一組。** 這需要設計方裁決,不是資料能決定的。

### 次要觀察

1. **FLIP 隨場地縮小單調下降**(26.2% → 11.0%)。場地小,車在被撞飛前就先出界。
   翻覆是這個遊戲較有觀賞性的結束方式,縮場地會壓抑它。

2. **角速度分布幾乎不隨場地變化**(p50 從 37.6 降到 30.8)。
   環繞不是被場地邊界逼出來的,是輪胎與驅動模型的性質 —— 與第一輪 μ 掃描的結論一致。
   五組 clamp 全程 0/0。

3. **圍欄最大誤差隨 R 縮小而下降**(3.02 → 1.51 mm)。
   26 段固定,R 越小弦長越短,折線逼近圓的誤差自然變小。無縫隙(落空 0)在五組皆成立。

4. **取樣拒絕率隨 R 下降**(12.9% → 8.3%)。合法區在外接矩形中的占比隨 R 縮小而上升。

5. **質心 y 峰值 S3 為 0.4047**,是五組最高,已接近 §11.2 的 0.5 門檻。
   單一場次的極值,樣本量不足以判定趨勢,但選定 S3 時須複查。

### 與第一次執行的差異

換用新餘裕後,五組的絕對數字都變了(投擲區縮小 4 cm,開場距離普遍拉近),
但**兩個主要結論都保住**:

| | 第一次(餘裕 0.08) | 第二次(餘裕 0.1201) |
|---|---|---|
| 逾時率最低組 | S2(10.4%) | S2(10.8%) |
| 逾時率形狀 | 非單調,S2 轉折 | 非單調,S2 轉折 |
| 秒殺率 | 單調上升 56.0% → 78.0% | 單調上升 52.2% → 77.0% |
| 刃口穿牆 | 1.6% → 4.7% | **全數 0.0%** |
| 生成穿插 | 未量測 | 4.5% → 33.0% |

## 2. 調參工作流

### 2.1 快循環（每次改參數都跑）

```bash
# 1. 改 src/data/constants.ts
# 2. 重新蓋章 version.ts 的 PHYSICS_CONSTANTS_SHA256
sha256sum src/data/constants.ts

# 3. 物理健全性（clamp、三模態、行駛高度、幾何斷言）
npx vitest run tests/acceptance.test.ts          # 14.0 s

# 4. 統計，與本文件 §1 逐項對照
npx tsx tools/baseline-report.ts                 # 8.8 s

# 5. 看成因（開疊圖，尤其是法向力柱與輪胎力箭頭）
npm run dev                                      # 1.2 s 起動
```

**一輪約 25 秒**（不含看畫面的時間）。

### 2.2 慢循環（選定一組參數後、升版前跑一次）

```bash
npm run check                                    # 170 s
npx tsx tools/verify-platform.ts --compare fixtures/platform/baseline.json   # 2.9 s
```

各步驟實測耗時：

| 步驟 | 耗時 |
|---|---|
| typecheck | 2.3 s |
| lint | 2.2 s |
| `tests/overlay.test.ts` | 0.2 s |
| `tests/replay.test.ts` | 2.9 s |
| `tests/render.test.ts` | 3.7 s |
| `tests/acceptance.test.ts` | 14.0 s |
| **`tests/determinism.test.ts`** | **147.5 s** |
| `tools/baseline-report.ts`（500 場，12 workers） | 8.8 s |
| `verify-platform --compare`（20 fixture） | 2.9 s |
| dev server 起動 | 1.2 s |

`npm run check` 的 170 秒有 **87% 花在決定性測試**上，而決定性與參數值無關 ——
它驗證的是「同一輸入重複執行結果相同」，改 μ 不會動搖這一點。
**因此快循環刻意不跑它**，只在選定參數後跑一次。

### 2.3 調參後會**正常變紅**的測試

以下失敗是預期的訊號，不是壞掉。逐項處理，不要為了讓它變綠而改回參數：

| 測試 | 為何會紅 | 處理 |
|---|---|---|
| `acceptance` → physicsVersion 與 constants 同步 | 常數雜湊變了 | 重新蓋章 `PHYSICS_CONSTANTS_SHA256`；確定要保留這組參數時同時把 `PHYSICS_VERSION` 升到 2 |
| `verify-platform --compare` | 物理變了，checksum 必然全部不同 | **預期** —— 這正是升版要重新產生 baseline 的原因（見 §3） |
| `acceptance` → 角速度統計基線（p90 < 80、peak < 140） | 這是 v1 的實測上界 | 依新實測值更新門檻，並在本文件記錄新舊值 |
| `acceptance` → 穩定產生 FLIP / OUT | 斷言了特定輸入的特定結局 | 依新物理重新挑選 sample battle，或放寬為「reason 屬於預期集合」 |
| `acceptance` → 靜態行駛高度落在 §7 的 y 下界之下 | 車體尺寸改變會動到行駛高度 | **必須連帶重算 §7 的 `y` 下界**（SPEC.md §7 有明文要求） |
| `replay` → sample battle 的結局斷言 | 同上 | 重新產生 `sample_battles/` 並更新 `_comment` 與 README 表格 |
| `render` → 五類結局皆可播放 | 若某個 sample 的結局改變 | 同上 |

**不會紅**（已刻意設計成從常數讀取）：幾何同步測試、疊圖換算測試、決定性測試、
`overlay` 的 `F/N = μ` 測試（μ 由 `TIRE_FRICTION_COEF` 讀入而非寫死）。

### 2.4 硬性約束（改參數時不得違反）

- **三模態 `|r| < 1`** —— 車體放大必然改變 `I_zz` 與輪距，`acceptance` 有自動驗算
- **clamp 觸發次數必須為 0** —— clamp 只攔數值發散，不得參與遊戲（SPEC.md §6.3）
- **`y > 0.5` 不得出現**
- **§7 的 `y` 下界須依新的實測靜態高度重新確認**
- 不得為了讓某項測試變綠而降低 checksum 精度或放寬比對容差

## 3. `PHYSICS_VERSION` 升版時的 baseline 歸檔

### 3.1 為何歸檔而非刪除

v1 的 baseline 是**跨平台矩陣的既有證據**。日後若某個平台出現分歧，
必須能回答「這是新引入的，還是 v1 就存在？」——沒有 v1 的 fixture 與 baseline 就無從判斷。

### 3.2 目錄結構

```
fixtures/platform/
  v1/                     ← 歸檔（唯讀，不再更新）
    head_on_01.json … orbit_04.json      20 組 fixture
    baseline.json                         v1 的參考結果
    ARCHIVE.md                            指紋、CI run 連結、歸檔日期
  head_on_01.json … orbit_04.json         現行（v2）
  baseline.json
```

`loadFixtures()` 只讀 `*.json`，子目錄會被自動略過，因此歸檔不會干擾現行組。

### 3.3 歸檔步驟

```bash
# 1. 歸檔 v1（用 git mv 保留檔案歷史）
mkdir -p fixtures/platform/v1
git mv fixtures/platform/*.json fixtures/platform/v1/

# 2. 寫 fixtures/platform/v1/ARCHIVE.md
#    須含：physicsVersion 1、Rapier 0.19.3、wasm SHA-256、CI run 連結、
#          八組平台矩陣結果、歸檔日期

# 3. 以新物理重新產生 v2 的 fixture 與 baseline
#    （fixture 的投擲參數可沿用 v1 的同一組，只有結果會不同；
#      若新物理下某類情境不再出現，才需要重新搜尋）
npx tsx tools/verify-platform.ts --generate --no-dense --out fixtures/platform/baseline.json

# 4. 推送後確認 CI matrix 對 v2 全綠
```

### 3.4 重跑歸檔版

`verify-platform` 已支援 `--fixtures` 指向任意 fixture 目錄
（本階段新增，否則歸檔的 baseline 無法使用）：

```bash
npx tsx tools/verify-platform.ts \
  --fixtures fixtures/platform/v1 \
  --compare  fixtures/platform/v1/baseline.json
```

**注意**：這只在把 `constants.ts` 也還原成 v1 的情況下才會通過。
歸檔的用途是「保留 v1 的證據以供事後比對」，不是「在 v2 的程式碼上重跑 v1」——
後者需要一併 checkout v1 的 commit。

### 3.5 一併需要歸檔或更新的項目

| 項目 | 處置 |
|---|---|
| `fixtures/platform/*.json` + `baseline.json` | 移至 `v1/` |
| `src/data/version.ts` | `PHYSICS_VERSION` 1 → 2，重新蓋章常數雜湊 |
| `sample_battles/*.json` | 重新產生（結局會變），更新 `_comment` |
| `fixtures/benchmark-500.json` | 投擲參數不變，**無須重產**（它只是輸入） |
| `README.md` 結案記錄 | 新增 v2 的平台矩陣結果，保留 v1 那一列 |
| 本文件 §1 | 新增 v2 基線區塊，**保留 v1 區塊作為對照** |
| 既有 replay 檔 | 自動失效 —— `physicsVersion` 不符會拒絕重現（SPEC_PHASE1.md §P1.4.2） |
